# When Does Batch Prompting Help LLMs? — план дослідження

Статус: драфт v1, 2026-10-28.
Основа: thesis proposal (`Batch Prompting for LLMs.pdf`), Cheng et al. 2023, Karpo & Chernodub 2026.

## Мета

Визначити, коли і чому batch prompting змінює якість виходу LLM, і побудувати
unsupervised-критерій, який без розмітки на цільовій задачі рекомендує:
чи батчити, який batch size, і який очікуваний напрямок зміни якості.

## Research questions

- **RQ1.** Як батчинг впливає на якість залежно від задачі, моделі та batch size?
- **RQ2.** Чи attention dilution є причиною змін (а не кореляцією)? Якщо ні, що є?
- **RQ3.** Чи можна передбачити напрямок і величину ефекту без розмітки?
- **RQ4.** Чи можна це зібрати в практичний інструмент?

## Задачі та дані

| Задача | Датасет | Метрика | Вісь, яку тестує | Роль |
|---|---|---|---|---|
| GEC | BEA-2019 dev (W&I+LOCNESS), CoNLL-2014 | ERRANT F0.5, M2 | довгий copy-heavy вихід | якір, відомий позитивний ефект |
| Arithmetic reasoning | GSM8K test | exact match | multi-step reasoning | очікуване падіння |
| Sentiment | SST-5, TweetEval-sentiment | accuracy, macro-F1 | короткий вихід, суб'єктивна шкала | anchoring-гіпотеза |
| ABSA | SemEval-2014 Task 4 (Rest14, Laptop14) | ATSC: accuracy / macro-F1; E2E pairs: F1 | структурований вихід, кілька відповідей | прямий тест cross-input leakage |
| Strategic QA | StrategyQA | accuracy | reasoning без арифметики | зв'язок із GSM8K |
| Table QA | WikiTQ | denotation accuracy | довгий структурований вхід | **held-out для RQ3** |

Уніфікований формат: `data/processed/<task>/<split>.jsonl`, рядок =
`{"id", "task", "input", "target", "meta"}`. `meta` зберігає все специфічне
для задачі (аспекти, таблицю, варіанти відповіді, M2-анотації).

Правила роботи з даними:
- WikiTQ не використовується до фінальної оцінки RQ3/RQ4.
- Для кожної задачі фіксуємо dev-сабсет (для відладки промптів) і eval-сабсет.
- Жодних правок промптів після запуску eval.

## Моделі

- Open-weight (RQ1, RQ2, RQ3): Qwen3-8B, Gemma-4-12B, + одна родина для
  перевірки переносу (Llama). Потрібен доступ до attention: HF Transformers,
  eager attention, хуки для статистик на льоту.
- API (RQ1, black-box гілка RQ3): 1–2 моделі (вирішити за бюджетом).
- Локальна машина (M4 Pro, 48 GB, без CUDA) підходить для підготовки даних,
  парсерів, метрик і прогонів 8B-моделей у 4-bit через MLX/llama.cpp для
  відладки. Для attention-аналізу та повних прогонів потрібен GPU в оренді.

### Фаза 1. RQ1: характеристика ефекту (тижні 4–11)

Протокол:
- batch sizes {1, 2, 4, 8, 16, 32}; temperature 0; один шаблон промпту з
  нумерованими входами і виходами; один парсер на задачу.
- zero-shot і few-shot окремо.

Контролі:
- ≥3 випадкові перестановки складу батчу на кожен batch size.
- Однорідні батчі (схожа довжина) проти змішаних.
- Parse failures та missing outputs рахуються окремо від якості.

Що міряти: основна метрика, Δ відносно b=1, довжина виходу, частка правок
(GEC: overcorrection rate), ефект позиції в батчі, частка розбіжностей між b=1
і b=k для одного прикладу, зайві аспекти у виході (ABSA).

Статистика: paired bootstrap CI; mixed-effects регресія
`Δ ~ властивості задачі + модель + batch size`.

Результат: таблиця результатів + перший список фіч-кандидатів для RQ3.

### Фаза 2. RQ2: attention dilution, причинність (тижні 10–17)

Сигнали (на токенах виходу, по головах і шарах): ентропія attention,
концентрація (top-k mass), частка уваги на власному вході / чужих входах
(leakage) / інструкції / sink-токенах.

Інтервенції:
- Маскування cross-input attention при тих самих позиціях.
- Заміна сусідів на нейтральний filler тієї самої довжини.
- Один приклад на різних позиціях при фіксованому батчі.
- Для сентименту: підбір складу батчу (всі негативні сусіди vs змішані).

Mediation analysis: batch size → attention-сигнал → якість, з контролем
за довжиною контексту.

Output-distribution shifts: KL між next-token розподілами при b=1 і b=k,
ентропія виходу, для GEC ймовірність copy-токенів.

Альтернативні гіпотези (перевіряти паралельно): in-batch ICL (сусіди як
демонстрації), регуляризація довжини/формату, позиційна деградація,
interference між прикладами.

### Фаза 3. RQ3: unsupervised-критерій (тижні 16–23)

Ціль: напрямок і величина Δ, оптимальний batch size для пари (задача, модель).

Фічі без розмітки:
- статистика входів/виходів з b=1: довжина, складність, розмір простору
  відповідей, наявність CoT;
- model-internal: Δ attention-сигналів, KL виходів, ентропія;
- black-box (для API): частка збігів між b=1 і b=k, зсув довжини виходу.

Побудова: прості правила/пороги → маленька модель, калібрована на dev-задачах.
Формулювання в тексті: критерій не потребує розмітки на цільовій задачі, але
калібрується на розмічених dev-задачах.

Оцінка: leave-one-task-out, leave-one-model-family-out. Метрики: точність
напрямку, кореляція передбаченої та реальної Δ, regret рекомендованого
batch size. WikiTQ як повністю held-out.

### Фаза 4. RQ4: інструмент (тижні 22–26)

Python-пакет/CLI: вхід = нерозмічені приклади + модель; вихід = рекомендація,
batch size, напрямок + confidence, оцінка економії токенів. Режими: HF
(з attention) і black-box (API). Валідація проти повних оцінок на held-out.
